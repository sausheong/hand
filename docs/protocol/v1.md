# Hand protocol version 1 (development)

This document describes the implemented development CLI event output and RPC contract. Released-package compatibility qualification remains pending; this is not a released compatibility promise. See [automation and the Go SDK](../automation-and-sdk.md) for client lifecycle and request recovery.

Each message is one UTF-8 JSON object followed by LF. CRLF is accepted as JSON whitespace before LF. The maximum encoded frame size is 1,048,576 bytes excluding LF. Blank frames are invalid requests. EOF between frames is normal; EOF before the required newline is a truncated-message error. An oversized frame is fatal to the connection: the receiver must close instead of interpreting the remaining bytes as another request.

During RPC initialization, at most one complete request can wait for the dispatcher. Clients should send `hello` and wait for its response before sending more requests. Additional queued startup frames fail with a startup backlog diagnostic on stderr and cancel construction; Hand joins owned startup children before exiting. After initialization, the normal bounded transport applies backpressure. EOF during initialization also cancels startup, including when the initial request is queued.

Requests carry `version`, `id`, `method` and an optional object-valued `params` (default `{}`). Version 1 is currently the only supported version. IDs contain 1–128 UTF-8 bytes with no control characters. Method names contain 1–64 ASCII lowercase letters, dots or underscores. Duplicate top-level fields, unknown envelope fields, trailing JSON values and invalid field types are rejected before dispatch. Method-specific parameter validation belongs to dispatch; envelope parsing does not authorise an operation.

Example request:

```json
{"version":1,"id":"request-1","method":"state","params":{}}
```

Responses carry `version`, `request_id` and a result or structured error (`code`, `message`). Events carry `version`, `event_id`, `sequence`, `session_id`, `run_id`, `request_id`, `timestamp`, `kind` and an object payload. Timestamps use JSON RFC 3339 time encoding. The event publisher and request ledger enforce identifiers and sequence semantics; clients must not infer them from arbitrary incoming JSON.

The shared writer marshals a complete JSON record before acquiring its write lock, then writes the frame without interleaving concurrent publishers. Any partial/error write poisons that writer: later writes return the prior error and do not append to a corrupt stream. The transport owner must interrupt blocked I/O by closing it. The connection owner bounds progress retention, reports cursor gaps and joins active work on disconnect. Durable request lookup provides retained terminal outcomes; progress events are not a durable replay log.

Permanent tests cover exact frame boundaries, duplicate IDs, unsupported versions, malformed/truncated input, UTF-8 validation, concurrent writes and a partial-write failure. A parser fuzz target is included. These tests establish framing behaviour only; they do not prove a usable RPC client journey, durable idempotency or interface approval parity.

## One-shot event output

The staged CLI now implements `--jsonl -p 'prompt'` for one-way application events. The accepted run emits ordered progress and exactly one terminal event after joining. Request ID is `oneshot`; event IDs are unique within and across invocations. No replay guarantee is implied yet. Tool/result payloads are bounded snapshots with explicit truncation. Diagnostics use stderr; pre-admission errors may exit without a run event. JSONL mode does not read stdin for workspace trust and does not accept approval responses. See `docs/acceptance/jsonl-events.md` for implementation scope and remaining transport work.

## Approval control methods

`approval.pending` returns pending approval events and a count remaining beyond the bounded response. `approval.respond` accepts an object containing `run_id`, `approval_id` and `decision` (`once`, `deny` or `always`). IDs must be copied from a current approval event. Cancelled, stale or already answered approvals are rejected. `always` requests the existing persistent grant behaviour and must be an explicit client/user choice. Preview text is informational and is not an authorisation token.

### Automatic follow-up continuation

`followup.enqueue` supports opt-in `auto: true` and returns the execution `request_id`. Automatic entries run in FIFO order after durable successful terminal results. Cancellation or failure pauses continuation; `state.followup_paused` reports this state and `followup.resume` explicitly resumes while idle. A manual entry at the head blocks automatic entries behind it. Queue intent is connection-local; durable execution records prevent automatic replay of prior intent. See `../acceptance/rpc-auto.md` for current development limitations.

### Durable control-operation replay

Session/profile mutations, queue controls, approval responses, cancel and followup.resume now retain their original responses in the ledger. Identical request-ID retries replay that response; changed payloads conflict. Incomplete prior controls return request_uncertain rather than executing again. This supersedes earlier development notes about non-execution mutations lacking deduplication. Control records use kind=control and operation_id; their result contains a protocol response rather than a run terminal event. See `../acceptance/rpc-control-ledger.md`.

### Scoped permission methods

Configured scoped-authority applications advertise permission.list (offset pagination, grants/next/total) and permission.revoke (id). Revocation responses use durable control-operation replay. Grants include operation/resource, scope, lifetime, provenance and workspace/configuration identity. Applications without scoped authority reject these methods.

`hello`, `state`, `cancel` and `approval.pending` require empty `params: {}`. Unknown fields return `invalid_params` before negotiation, cancellation or other method effects. Rejected `cancel` requests retain their response: retrying the same ID and payload replays the rejection, while changing the payload requires a new request ID.

Completed prompt-ledger records retain a full terminal event. Before writing or
replaying one, Hand checks its protocol version, request/session/run identities,
event ID, sequence, timestamp and terminal kind. Its outcome must use a supported
status, nonempty reason and explicit boolean verification value; a failed or
cancelled outcome cannot be verified. Duplicate terminal fields and case aliases
of outcome fields are rejected. Corrupt persisted completion records refuse to
open without modifying the ledger or granting a fresh execution attempt. These
checks establish record consistency, not independent proof of task correctness.

Ledger envelopes and completed control responses also require canonical, unique
field names. Control errors contain exactly `code` and `message`, both strings,
with a nonblank code. An empty message is permitted; a null error object is not.
Ambiguous saved responses fail reopening without rewriting the ledger, and valid
restored records retain their original replay protection.

### Usage certainty

A usage payload keeps reported token subtotals separate from completeness:

- `reported_totals_known` means that the included counters represent an available
  reported subtotal. A subtotal of zero does not prove zero total consumption.
- `known` is true only when that subtotal is available, `unknown_requests` is zero
  and `prior_unknown` is false.
- `unknown_requests` counts recorded attempts without reported usage.
- `prior_unknown` records unknown historical consumption independently of the
  number of tracked attempts.

For example, nine requests without provider usage produce `requests: 9`,
`unknown_requests: 9`, `known: false` and `reported_totals_known: true` in a saved
session summary. Reported token subtotals are zero; actual consumption is unknown.
An event with only historical uncertainty still includes its usage payload.

Earlier development encoders used `known` to indicate subtotal availability.
Durable replay preserves original event bytes. Consumers reading those records
must check `unknown_requests` and `prior_unknown` before claiming complete totals;
absence of `reported_totals_known` does not resolve historical uncertainty.

### Canonical method parameter fields

Top-level method parameter names must exactly match the declared schema. Duplicate decoded names (including escaped spellings) and case aliases are rejected before method effects. A second `confirmed` field cannot replace a prior value. Nested objects retain method-specific validation; tariff arrays additionally reject ambiguous rate fields through the shared price-table decoder.

### Cancellation when request storage fails

If the request journal is closed or poisoned by a write failure, a valid `cancel` with empty parameters still signals active application, extension and verification work and pauses automatic follow-ups. The response is `ledger_failure`, with no success result: neither a durable cancellation receipt nor a durable terminal outcome is promised. Inspect/reconcile the prior request after recovery; do not assume completion or resubmit its work under a new ID. Malformed cancellation parameters and request-ID conflicts while the journal is healthy do not trigger this fallback. New work remains denied while the journal is unavailable.

`context_usage` reports the most recent provider request input occupancy, separately from cumulative `usage` and `session_usage` totals. Its usage payload uses `known: false` when the request supplies no measurement. Cached input is already included in canonical input tokens and must not be added again. The TUI clears its context gauge after model/session changes or compaction until another request reports usage.
