# Application lifecycle ownership

Status: accepted direction; CLI migration implemented, TUI migration in progress.

The application service owns a user goal across backend turns and completion checks. A backend stream closes only after that turn's deferred cleanup joins. The service evaluates mandatory completion checks after this close, including the final allowed iteration, and emits exactly one terminal event for an accepted operation. Concurrent requests are rejected with ErrBusy without inventing a second terminal outcome.

Cancellation requests change the active state to cancelling but do not release ownership. Backend and completion-check workers must return before a subsequent operation can begin. Cancellation and terminal commitment share a mutex: a cancellation accepted before the commit wins; a later cancellation returns false. This avoids reporting success after accepting cancellation at the final boundary.

Application events contain value fields: session/run identity, service-wide sequence, UTC timestamp, state, text and terminal outcome details. Error text is captured when published. Sequence numbers define ordering; wall-clock timestamps are observational. Run/sequence counters currently belong to one service lifetime. Durable restart identity belongs to the session/protocol work and is not claimed yet.

The initial internal API is synchronous Execute with a serial consumer callback that must return promptly and a separate thread-safe Cancel operation. A blocked consumer can delay execution; it must return promptly. This is the CLI integration boundary, not the final RPC/SDK subscription contract. The next migration must provide bounded transport/event delivery without allowing slow or disconnected consumers to prevent cancellation and cleanup.

The CLI now renders text, turn separators and continuation notices from this operation. Its iteration and completion logic has moved out of main.go. The Harness adapter currently translates the events needed by that text interface. TUI tool/usage rendering, approval request lifetimes, model/session switches and compaction must move onto the shared service before M2.1 can pass. The defined awaiting-approval/compacting states do not imply those operations have already migrated.

The current released Harness persists during session operations but may log persistence failures without surfacing them. Joining a backend is not proof of successful durable persistence. M3's persistence/error propagation must prevent successful terminal claims when required durable state cannot be established. No public SDK may expose mutable runtime pointers as a shortcut around ownership.

The TUI's controller implementation has now moved into app. Its turn adapter and configuration/compaction methods reserve the same service operation gate. Cancellation retains this reservation until the runtime stream or compaction worker returns. Switch/session operations reject active background compaction instead of mutating its configuration. Production TUI code uses controller methods and no longer accesses Rt fields. The retained Controller type alias is internal compatibility for construction/tests, not a public runtime API.

Cross-provider model switches construct the replacement using the new provider's default endpoint; they never inherit a previous custom endpoint. A construction failure commits nothing. Same-provider switches preserve the current endpoint, fallback and compaction client. Explicit selection of custom destination profiles is still M2.2 work. The TUI's top-level goal/check/approval coordination remains to be migrated; the transitional turn adapter is not the final shared goal subscription.

Start now provides an asynchronous stream and claims operation ownership before returning. Progress uses a 64-event queue with text chunks capped at 16 KiB; valid UTF-8 is preserved. The queue therefore retains at most 1 MiB of text payload plus fixed event overhead. This bound excludes the current backend-supplied event, request images and backend/provider allocations; it is not a whole-process memory claim. Large text is cloned into independent chunks rather than retaining a large source string through each queued substring. Continuation display/error metadata is explicitly marked when truncated; the actual continuation prompt and original error chain remain intact internally.

Terminal delivery has its own single-element channel. Cancellation unblocks a producer waiting on progress delivery and still joins its backend/checker. Read progress through closure before displaying the terminal event to maintain order. Close requests cancellation on disconnect; Wait joins the operation and preserves the original outcome/error chain. A client that never consumes or closes its stream can apply backpressure, but cannot cause an unbounded queue. Image input bytes are copied before Start returns.

Cancellation handles are tied to a separate operation generation, which advances for runs and configuration/compaction reservations. An old run handle cannot cancel a later run or compaction. CLI rendering now consumes this stream. Full TUI goal, tool-event and approval migration remains required.

The Harness adapter now captures tool calls/results, usage and compaction into value-only Details. Mutable JSON input and metadata are copied to strings, images are represented by their count, and usage presence is separate from its counters. Counters retain released Harness v0.3.9 semantics until the accounting migration; these events are not yet a request ledger. Runtime aborts become failures even if another done event exists.

Details has a separate aggregate 16 KiB bound across all strings, including tool display IDs. Truncation is explicit; truncated JSON strings are display text, not parseable protocol payloads, and these IDs must never authorise actions. Each event can retain up to 16 KiB each for text, error and aggregate details (a conservative 3 MiB across 64 queued events), plus identity/fixed overhead. Metadata serialization and the current runtime event can temporarily allocate beyond this queue bound. Full tool artifacts, image retrieval and durable structured transcripts remain future work. The TUI still uses the transitional runtime adapter pending full goal/approval migration.

Production TUI construction now selects the same Service.Start goal operation used by the CLI. Bubble Tea pulls one immutable application event per command and schedules the next read after rendering, avoiding a separate unbounded forwarding queue. The stream exposes a copied RunIdentity before Start returns, allowing approval messages to match the service context even when a backend starts immediately. Terminal outcomes come from Stream.Wait after ownership release and checker/backend join; the TUI does not rerun Stop hooks on this path. It stays running during completion checking, so cancellation and configuration guards remain effective. Program.Run exit also cancels and joins the active goal.

The legacy Runner path and its coordinator remain for existing internal tests/embedders during migration. Production selects the shared service explicitly. Approval rendering and response channels still live in the existing agentio/TUI bridge; application-owned awaiting-approval state and a reusable approval protocol remain unfinished. These changes do not close M2.1 or prove persistence/recovery acceptance.

Interactive approval lifetime now belongs to Service. Its hook adapter reuses agentio operation classification and permission persistence, but sends approval_required/approval_resolved/warning through the bounded application stream. RespondApproval requires the full run identity and an opaque request ID and accepts each valid decision once. Cancelled, completed, mismatched and duplicate decisions fail. Display strings and truncated identifiers are never used to identify the authorised operation. Pending requests retain the original operation input in the hook; displays remain bounded and explicitly marked when truncated.

The service enters AwaitingApproval while requests are pending, resumes Running before the final resolved event, and removes requests before their backend worker returns. The registry is capped at 64 concurrent requests; overflow is an explicit operation error. Context cancellation unblocks request delivery and decision waits, including an unread progress queue. The TUI uses RespondApproval instead of response channels on the production path, and the obsolete main programSender bridge is removed. Legacy internal tests/embedders still have the old channel adapter. One-shot operation policy continues to resolve noninteractive approvals directly. Durable grants with exact scopes remain M5 work.

ModelInfo is now included by value in every application event. Profile switches update its requested identity and context provenance under the same operation reservation; prior events cannot change. Its variable-size strings share a separate 16 KiB aggregate display bound. Together with text/error/details this gives a conservative 4 MiB across 64 progress events, plus fixed and identity overhead. ModelInfo display fields are not selection or approval capabilities. Unknown serving identity stays unknown even when a requested aggregator alias is present.

Production terminal construction now requires NewApplicationModel(service, workspace). A missing service returns an error, and the terminal installs no Runner or separate Stop-hook configuration. SetService is removed: callers cannot replace ownership after construction. The old Runner-accepting NewModel exists only in test code for fixtures awaiting migration. Legacy runtime event and goal handlers still remain in the production package and must be removed after those behaviour assertions move to service-backed journeys.

The duplicate TUI goal loop is now removed: no goalLoopResultMsg, asynchronous Stop checker, auto-continuation launcher or hook configuration remains in terminal production source. Completion checks and continuation decisions belong to app.Service. The older single-turn runtime/event adapter still exists for unmigrated fixtures and is the next removal target.

The single-turn terminal runtime adapter is removed as well. TUI Model has no Runner/runtime field, raw AgentEvent renderer or forwarding goroutine. User requests and queued work enter the shared service; application messages carry ordered progress and joined terminal outcomes. Transitional Controller.Run and legacy channel-based approval compatibility are separate remaining cleanup, as is runtime construction in main.

Terminal approval compatibility is removed: raw ApprovalRequest/ApprovalWarning messages are no longer accepted, and no response-channel fallback remains. UI decisions go through the active service with an opaque request ID and full run identity. Rendering-only fixtures may still construct pending display records, but these cannot authorise an operation.

Startup construction attempts now use app.StartupAttempt: cancellation is nonblocking, Finish joins and disposes failed or abandoned runtimes, and only a completed successful attempt transfers ownership. The terminal startup model retains draft/status rendering and retry selection. CLI dependency composition is still a remaining extraction boundary.
